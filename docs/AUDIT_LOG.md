# 監査ログ（audit_log）

更新系の API 要求と認証・ユーザー管理のイベントを記録するテーブル。マイグレーション 0004 で作成し、0044 で追記専用にした。

## 追記専用（0044）

`audit_log` への UPDATE・DELETE・TRUNCATE は DB のトリガで拒否する。INSERT とバックアップからのリストアはこれまでどおり行える。

さらに、backend の接続ロール `cpim_app` には `audit_log` の SELECT と INSERT しか与えていない。所有者でもないのでトリガも外せない（`docs/DB_ROLES.md`）。
DB の管理権限（`cpim`）があればトリガを外せるので、その資格情報は厳重に扱う。

## 記録の仕組みと限界

- 記録は業務処理の後に、別のトランザクションで行う。業務処理の結果は記録の成否に左右されない。
- 記録に失敗すると、サーバーのログに `audit record failed` を出す。このログが出た時刻の操作は監査ログから抜けている。
  業務のコミットと記録の間にプロセスが落ちた場合も抜ける（この場合はログも出ない）。
- ハンドラがパニックした要求は、`http_status=500` で記録する。
- 未認証、または CSRF で拒否された要求は記録しない。
- 本文が 1 MiB 以上、または長さが不明な要求は、`payload` を記録しない。
- 新規作成の要求では `resource_id` は空になる（`action` のパスと `payload` で確認する）。

## 保持期間

保持期間は未定で、削除の処理は無い。追記専用のため、古い行を消すにはトリガの扱いを含めて手順を設計する必要がある。
