- ベースライン: v0.41.1（`f7c6491`）

- マイグレーション: 0001–0042（今回の修正で追加したマイグレーションは無い。0041 以前のファイルは不変）

## 主な機能（Migration 0042）

0041 の副作用の無い Simulation/Publish とは別の実行境界として、承認済みのリカバリ計画を業務データに適用する Controlled Recovery Plan Execution を追加した。詳細は `docs/0042-controlled-recovery-plan-execution.md` と `RELEASE-METADATA.txt`。

## 移行後に入れた修正

いずれも v0.42.0 に含まれる。不具合の詳細は `docs/TEST_FINDINGS.md` の「修正済み」。

### 常に失敗していた機能（PR #7）
- 作業指示の完了・進捗報告、監査ログ一覧、S&OP 製品構成バージョンの有効化・一覧が必ず失敗していたのを修正。

### 業務日付（PR #8）
- 日付の比較・集計・「今日」を業務タイムゾーン（既定 Asia/Tokyo、DB の `eco_business_timezone()` と一致）の暦日に統一。サーバーの TZ によって結果が変わっていた。

### 計算の誤りとデータ破壊（PR #9）
- CTP: 2 階層で使われる部品を同じ空き在庫で二重に判定し、不足でも「今日可能」と回答していた。
- ABC 分析: 使用金額 1 位の品目が B/C になり得た。
- 安全在庫: 品目マスター値へのフォールバックが到達不能で、履歴の短い品目の平均が薄まっていた。
- CSV 取込: 既存品目の更新で CSV に無い計画パラメータが初期値に戻っていた。負の値など範囲外の値を受け付けていた。

### リカバリ計画の実行（PR #10）
- 同じ実行の中で 2 つのアクションが同じ部品・同じ残業枠を使うと、自分自身の変更をドリフトと判定して PARTIAL_FAILED になっていた。

### 同時実行（PR #11）
- 同じ実行計画への Execute が同時に来るとデッドロックし、リトライ上限を超えて 409 になっていた。
- 同じ発注への供給者スケジュールの記録が 6 件以上同時だと、リトライ上限を超えて失敗していた。

### API（PR #3・#4・#12）
- エラー応答に内部の詳細（SQL エラー、制約名）を出さないようにした。シリアライズ失敗は自動でリトライし、業務ルール違反は 4xx にした。
- 存在しない ID は 404、重複登録や使用中データの削除は 409 にした。

## 運用上の注意（挙動の変化）

- **API のステータスコード**: これまで 500 や 204 だった場面の一部が 404 / 409 になる。
  - 存在しない ID の取得・削除 → 404
  - 品目・顧客・受注の重複登録、使用中の作業区の削除 → 409
- **`X-Request-Id`**: クライアントが送った値を採用せず、常にサーバーが生成した ID を返す。
- **日付のみの入力**（`/api/abc-analysis?asOf`、受注・供給者スケジュールの日付）: `YYYY-MM-DD` に加えて RFC3339 も受け付ける（業務日付として解釈）。
- **リカバリ計画**: 計画全体としてしか成り立たない操作（同じ作業指示の二重リリース、合計で日をまたぐ残業など）は、承認前の事前チェックで BLOCKED になる（これまでは途中まで実行してから失敗）。
- **CSV 取込**: `domain.Item` と同じ範囲検証を行う。範囲外の行は取り込まれない。
- **シフト時間帯**: 作業区の `shiftStartMinute` は UTC 0 時からの分として扱う（従来どおり。480 = 8:00 UTC = 17:00 JST）。業務日付とは基準が違う。
